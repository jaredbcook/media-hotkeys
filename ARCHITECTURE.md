# Architecture

## Overview

A browser extension that adds keyboard shortcuts to control HTML media (`<video>` and `<audio>` elements) on any webpage, including media embedded in iframes or Shadow DOMs.

## Target Browsers

- Chrome
- Edge
- Firefox
- Safari (manual macOS/Xcode conversion from the Chrome build)

Uses `webextension-polyfill` to normalize `chrome.*` vs `browser.*` APIs across browsers.

## Manifest Strategy

- Manifest V3 for Chrome, Edge, and Firefox
- Manifest is generated per browser from `manifest.template.json`
- Safari wraps the Chrome Manifest V3 extension after building for Chrome first
- Frame isolation per Manifest V3 security model

## Content Script (`src/content.ts`)

- Runs on every page, injected into all frames
- Detects `<video>` and `<audio>` elements dynamically (including Shadow DOM)
- Listens for keyboard events and translates them to media control and overlay-display actions
- Communicates with iframes via `postMessage` API for cross-frame control
- Tracks "last interacted media" to intelligently select which media element to control
- Ignores input if focused element is an `<input>`, `<textarea>`, `<select>`, or is `contenteditable`

## Smart Media Selection (weighted scoring)

Every valid-source media element in the frame is scored, and the highest-scoring element above zero becomes the target (ties resolve to earliest DOM order). Signal weights are ordered by strength of user intent:

| Signal                                      | Weight     |
| ------------------------------------------- | ---------- |
| Fullscreen, PiP, or theater-mode element    | +1000      |
| Focused element                             | +800       |
| Playing and audible (unmuted, volume > 0)   | +500       |
| Last interacted media (click/play/focus)    | +300       |
| Last media actioned by the extension        | +200       |
| Playing but muted                           | +150       |
| Pointer hovering over it (non-ambient only) | +120       |
| Visible viewport area (proportional, video) | up to +200 |
| Audio element base (no visual footprint)    | +20        |
| Native controls present                     | +30        |
| Non-ambient base                            | +10        |
| Ambient-looking (muted video, no controls)  | −250       |

"Playing" means not paused or ended with at least metadata loaded, so media that is momentarily buffering keeps its playing score.

Clicks count as interactions whether they land on the media element or anywhere inside its box: custom players (YouTube, Vimeo, Video.js, Plyr, MediaElement) stack their controls over the `<video>`, so presses on their play/mute/seek buttons never reach the media element. A capture-phase `pointerdown` listener on the document attributes such presses to the innermost visible media under the pointer.

The ambient heuristic is a penalty, not an exclusion: a muted no-controls video can still be targeted when stronger signals apply — the user focuses or clicks it, it occupies a large visible area (the autoplay-muted primary-content pattern), or the extension already acted on it (`actionedMedia` retains its standing). An idle background loop scores below zero and is never selected.

**Edge Cases:**

- Multiple playing media: audible beats muted; among equals, recency and visible area decide, then DOM order
- Iframe media: resolved via cross-frame score arbitration (see Cross-Frame Communication)
- Shadow DOM: recursively searched via `findMedia()`
- Interaction memory persists through unrelated DOM mutations and is dropped only when the tracked element leaves the document

## Cross-Frame Target Arbitration

Media actions are executed by exactly one frame, chosen by a two-phase protocol:

1. **Scoring phase** — the initiating frame scores its local candidates and sends a `SCORE_REQUEST` to child frames. Each child recursively reports the best score in its subtree (within a shrinking time budget) and records which descendant owned it, keyed by request id.
   Each response also carries the visible-area component of the score. Because a child measures area against its own viewport, the receiving frame rescales that component by the fraction of its viewport the iframe visibly covers, so a video filling a small ad iframe (or an iframe scrolled out of view) cannot claim the full area score.
2. **Execute phase** — the initiator compares local vs. child scores (local wins ties) and sends the action to the single winning frame, which routes it hop-by-hop to the recorded winner. On failure or timeout the initiator falls back to its best local candidate.

A fast path skips the cross-frame round-trip when local intent is unambiguous (focus, fullscreen, PiP, or theater mode). When no frame has scorable media, placeholder activation is offered locally first, then broadcast to child frames as a last resort. Global actions (e.g. overlay toggle) intentionally keep broadcast cascade semantics.

## Playable Placeholders

Many pages show a thumbnail "facade" and only create the real player on click (YouTube's cued embed, `lite-youtube`, WP Rocket's lazy YouTube, Skool-style attachments). When no frame has scorable media, `placeholder.ts` scans for the best placeholder and clicks it, then plays the media that appears.

- A candidate needs a visible, thumbnail-sized box with duration text plus a play control or thumbnail. With no duration text, it needs both a thumbnail and an unambiguous play control: a button whose accessible name says "play" (aria-label, aria-labelledby, title, or short visually hidden text, in several languages), or a centered overlay following the play-button class-name convention (`vjs-big-play-button`, `lty-playbtn`, `.play`).
- "Watch" is not a play label; on real pages it marks navigation ("Watch on YouTube", "Watch later").
- The innermost qualifying candidate wins over wrappers that inherit its signals.
- Pressing play never navigates away. Cards whose click target sits inside a link to another page on the same site (search results, talk grids, "more videos" rails) are skipped, because SPA routers intercept those clicks. For links to other origins (facades that link to the provider as a no-JS fallback), the click goes through but any navigation the page itself did not claim with `preventDefault` is cancelled.

## Third-Party Player Compatibility

The extension is native-media first: it targets real `HTMLMediaElement` instances whenever possible, then uses narrow custom-player host APIs only when the media is inside an open Shadow DOM custom element. Provider iframe players and closed shadow roots remain best-effort.

### Player Landscape

| Player / Tech                              | Common Shape                                                           | Custom Player?                   | Direct `<video>`/`<audio>` Control Likely OK?                                                                               |
| ------------------------------------------ | ---------------------------------------------------------------------- | -------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| YouTube                                    | Cross-origin iframe, IFrame API                                        | Yes                              | Usually only from inside the iframe document; provider API exposes play, pause, seek, volume, mute, and rate controls.      |
| Vimeo                                      | Cross-origin iframe, Player SDK                                        | Yes                              | Usually no from the parent page; provider SDK exposes play, pause, current time, volume, rate, fullscreen, and PiP methods. |
| TikTok Embed                               | Provider embed or iframe                                               | Yes                              | Low confidence; treat as provider-owned custom embed.                                                                       |
| MediaElement.js                            | Custom UI over HTML5 media                                             | Yes, native-backed               | Usually yes when the underlying media element is reachable.                                                                 |
| Video.js                                   | Custom UI over native media; newer work includes Web Components        | Yes                              | Usually yes for native-backed players; Web Component hosts may also expose host APIs.                                       |
| Wistia                                     | Aurora `<wistia-player>` Web Component; iframe fallback                | Yes                              | Often yes, but host APIs are preferred when reachable for state sync.                                                       |
| Brightcove                                 | Hosted custom player with Video.js lineage                             | Yes                              | Often yes, but player APIs are safer for ads, analytics, and UI state.                                                      |
| JW Player                                  | Custom JavaScript player                                               | Yes                              | Often yes after setup, but JW Player exposes its own play, pause, seek, mute, and volume APIs.                              |
| SoundCloud                                 | Provider iframe/audio embed                                            | Yes                              | Usually provider-owned; direct media may not be reachable from the parent page.                                             |
| Vidyard / Loom                             | Provider iframe/player SDK                                             | Yes                              | Usually API or iframe-owned; frame-local media discovery may help when accessible.                                          |
| Flowplayer / Plyr / Fluid Player / DPlayer | Custom controls over native media                                      | Yes, native-backed               | Usually yes unless wrapping YouTube/Vimeo provider embeds.                                                                  |
| dash.js / hls.js / Shaka                   | Streaming engines attached to native media, sometimes with optional UI | Mostly not a UI player by itself | Yes; these libraries normally attach to a real media element.                                                               |
| Kaltura / Dailymotion / Twitch             | Provider iframe/player SDK                                             | Yes                              | Usually API or iframe-owned; frame-local media discovery may help when accessible.                                          |
| Bitmovin / THEOplayer                      | Commercial custom players                                              | Yes                              | Mixed; direct media may work, but player APIs are more semantically correct when available.                                 |

### Compatibility Model

- Provider iframe players usually require provider APIs or frame-local media discovery. The extension does not inject provider SDKs or add per-provider adapters by default.
- Native-backed custom UI players usually work through direct `HTMLMediaElement` control, so direct media control remains the default fallback for every action.
- Web Component hosts may need host APIs for state sync. For open-shadow custom elements, `content.ts` tries high-confidence native-equivalent host operations before falling back to the media element.
- Extension content scripts run in an isolated world by default, so page-defined custom element methods may not be visible to `content.ts`. A small `player-bridge.js` content script runs in the page's main world and handles only whitelisted synchronous host operations via DOM events and temporary `data-media-hotkeys-*` attributes. See Chrome's [`content_scripts.world`](https://developer.chrome.com/docs/extensions/reference/manifest/content-scripts) documentation and MDN's [`content_scripts`](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_scripts) reference.
- Closed shadow roots, unavailable provider frames, blocked autoplay, and player API failures are best-effort. Failures fall back to direct media control when possible and should not surface errors to users.
- Do not add generic button-clicking beyond the play-button fallback. Clicking arbitrary mute, seek, speed, fullscreen, or PiP buttons is too likely to hit the wrong control or double-toggle state.

## Key Design Patterns

**Dynamic Media Detection:**

- `findMedia(root)` recursively searches DOM and Shadow DOMs
- `MutationObserver` watches for newly added video/audio/iframe elements
- Only initializes event listeners if supported media elements or iframes exist

**Cross-Frame Communication:**

- Uses `postMessage` for the two-phase score/execute arbitration protocol (see Cross-Frame Target Arbitration)
- Uses `postMessage` to propagate top-level site policy into child frames
- Embedded frames inherit a disabled top-level site policy by default; a matching top-level rule can set its embeds policy to ignore so child frames are not disabled by that parent page rule
- Each frame runs its own content script instance independently
- Frame isolation by design (per Manifest V3 security model)

**Overlay System:**

- Creates temporary, absolutely positioned `<div>` over media elements
- Auto-removes after brief fade-out animation
- Displays action icons (Material Symbols) + numeric values (speed, seek duration)

**State Management:**

- `lastInteractedMedia` — most recently interacted media (click/play/focus); a weighted-scoring signal, cleared only when the element leaves the DOM
- `pointerPosition` (in `media-tracking.ts`) — last pointer position in the frame, for the hover signal; cleared when the pointer leaves the document
- `lastActionedMedia` / `actionedMedia` — media the extension itself acted on; scoring signal and ambient-penalty exemption
- `executeRoutesByRequestId` — short-lived routes recorded in the scoring phase so execute requests reach the winning frame
- Grouped settings model:
  - `quickSettings` contains the global enabled toggle and action key bindings
  - `advancedSettings` contains playback, seek, overlay, and debugging behavior
  - `siteSettings.sitePolicies` contains autosaved URL-ish rules with `disabled` or `enabled` page modes and an `inherit` or `ignore` embeds policy

## Default Settings

### Playback Speed

- **Min:** 0.25x | **Max:** 4x | **Step:** 0.25
- Clamp at boundaries — do not wrap around

### Skip Step Sizes

- **Small** (e.g. `ArrowLeft`/`ArrowRight`): ±5 seconds
- **Medium** (e.g. `J`/`L`): ±10 seconds
- **Large** (e.g. `[`/`]`): ±30 seconds

### Volume

- **Step:** 5% per keypress (0–100% range, clamped at boundaries)

## Key Technical Challenges

### Finding the Correct Media Element

Pages often contain multiple `<video>` and/or `<audio>` elements (ads, thumbnails, background videos). The content script must be injected into every frame and use `postMessage` for cross-frame communication.

### Site Conflicts

Sites like YouTube have their own native keyboard shortcuts. Media Hotkeys captures mapped keys before most page handlers by default, but users can add site policies such as `youtube.com` disabled and `youtube.com/shorts` enabled from Advanced Settings. More specific path rules override broader domain rules. Top-level disabled policy is forwarded to child frames by default so iframe handlers cannot bypass a disabled page, and each matching top-level rule can set its embeds policy to ignore when child frames should keep handling Media Hotkeys.

### Theater Mode

Theater mode promotes the target `<video>` into the browser's top layer as a manual popover rather than moving it into a dialog. The element never changes DOM position, so player scripts, framework reconcilers, and wrapper CSS that reference it keep working, and the top layer escapes ancestor transforms, `overflow` clipping, and stacking contexts. Sizing rules are `!important` inside a cascade layer so they beat both unlayered `!important` site styles and inline sizes that player scripts rewrite on resize. Site-drawn controls and caption layers stay behind in the page, so native `controls` are enabled for the duration and the action overlay is promoted into the top layer too. `Esc` or the hotkey exits and restores the original scroll position.

For a video inside an iframe, each ancestor frame promotes the `<iframe>` hosting it the same way, so the video can fill the top-level viewport. A child asks its parent with a `MEDIA_HOTKEYS_THEATER` message, and the parent enlarges the iframe only when it has a reason to trust the request: either it routed `toggleTheater` to that exact frame under the `requestId` the message carries (within the route TTL), or that iframe is the focused element in the parent (following focus into open shadow roots), which is the case when the user clicked into an embed and pressed the hotkey there. The parent then repeats the request to its own parent, passing along its own routed `requestId` when it has one and otherwise relying on the same focus check one level up. Without these checks, any embedded frame (an ad, for example) could post the message to cover the page; the remaining exposure is an iframe that holds focus, which in current browsers generally requires the user to have interacted with it. Exits need no trust: a frame that leaves theater mode notifies its parent and its promoted child, and each side ignores notices that don't match its state.

### Safari Conversion

Do not target Safari during active development. Build and stabilize for Chrome, Edge, and Firefox first, then run the Xcode converter as a final step.

### Closed Captions (Cross-Browser)

Native `<track>` elements can be toggled via the `TextTrack` API. Platforms like YouTube use custom CC UI, so per-site handling will be required.
